# Use an asynchronous terminal Compiler close lifecycle

Unpack will keep one active manual run per Compiler and deliver every accepted run callback asynchronously, including concurrent-run and closed-Compiler errors. The running state remains active through result normalization, logging, output completion, and other terminal preparation, then clears immediately before callback delivery so a successful callback may synchronously start another run. Compilation Errors continue through Stats with a null callback error, while infrastructure failures use the callback error channel without Stats. webpack's concurrent-run callback is synchronous; retaining Unpack's consistently asynchronous conflict callback is a Documented Webpack Deviation.

Compiler Close will use an explicit `open`, `closing`, and `closed` lifecycle. Close with active run or watch work reports an asynchronous `CompilerRunningError` and leaves that work intact. Idle close enters `closing` before returning, rejects new run and watch work, coalesces concurrent close callers onto one operation, waits any pending cache settlement, invokes native cache shutdown, releases the native Compiler handle, and only then delivers each close callback exactly once. A closed Compiler rejects later runs, while repeated close calls complete asynchronously with success. Persistent Cache publication diagnostics remain best-effort Infrastructure Logging under ADR 0133 rather than close errors.

webpack close may complete synchronously, may run while a Compilation is active, does not make the Compiler terminal, and permits a later run. Unpack deliberately keeps the terminal lifecycle required by Rust-native cache and resource ownership. This decision reaffirms ADRs 0053, 0054, 0055, 0063, and 0076, applies ADR 0133's best-effort cache failure rule to shutdown, and extends ADR 0135's caller-owned top-level Compiler lifecycle. Watching close and Watch Session recovery remain separate lifecycle decisions.
